## QA Summary

All eight wallet operations were exercised against the live dev stack with four fresh people: A (verified owner), B (verified, seeded as editor and later made owner), C (verified viewer) and U (unverified). Users were created through the app's own factories in `dev tinker`, which works outside a transaction since R-13, and signed in through `POST /auth/login`. Before B9, the editor and viewer memberships were inserted directly under the wallet lock.

Coverage:
- every acceptance scenario of US1–US4, and the HTTP-reachable part of US5;
- the spec's edge cases and the contract's field-level codes;
- the collection grammar;
- drift repair through `wallets:verify-balances`;
- five concurrent stale writes (exactly one lands).

The first run surfaced two failures, both test-script errors and not defects:
- TC-034 resent the transfer as the new owner rather than the previous one.
- TC-057 paged when only one wallet was live.

Both were corrected, and the full run is 67/67. The mobile-team bug (a late welcome mail superseding a newer verification link) was confirmed in code, fixed, and verified (see Failure Details).

## Failure Details

No acceptance failures.

### Mobile-team report: a late welcome mail supersedes a newer verification link (fixed)

**Status**: fixed in this change.
**Steps to reproduce** (before the fix):
1. Register. `SendRegistrationMail` is queued on the database queue.
2. Before the worker runs, the person asks for a resend: `LinkRepository::issue(VerifyAddress)` mails link L2.
3. The worker runs the welcome job, which calls `issue()` again. That supersedes L2 and mails L3.

**Expected**: the latest issued link (L2) stays valid.
**Actual**: L2 was superseded and its click failed with `VERIFICATION_TOKEN_INVALID`.
**Fix**: the job now uses `LinkRepository::issueFirst()`, which issues only if no link of that kind was ever issued. Issuing is serialised per person and kind with a PostgreSQL advisory transaction lock, and the job issues and sends in one transaction.
**Evidence**: `tests/Feature/Identity/VerificationLinkTest.php` (three new tests). A dev-stack replay (register → resend → late job) left the newest link unsuperseded.
**Severity**: High (it blocks verification, which gates every write).
