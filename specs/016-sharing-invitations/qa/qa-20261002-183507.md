# QA Report: Sharing & Invitations (spec 016, B9)

**QA Mode**: CLI QA. HTTP was driven by Python `requests` (curl-equivalent) against the running dev app. Server-side steps (seeding people, granting and revoking Plus, ageing an invitation, time-shifting one occurrence, reading rows for at-rest checks) ran as PHP in the `dev` container. Mail was read from Mailpit (`http://mailpit.test`).
**Date**: 2026-10-02
**Feature**: [spec.md](../spec.md)
**Environment**: Fedora Linux 44 (kernel 7.2.7) host; `dev` container with PHP 8.5 and PostgreSQL 16; http://saveme-backend.test/api/v1
**Verdict**: ✅ ALL PASSED. One copy defect in the invitation mail was fixed (see Failure Details). Every other first-run failure came from the test script.

---

## QA Summary

**Setup**
- Ran `dev queue:restart`. The supervisor in the `saveme-backend-main` container runs `queue:work` (database queue) and `schedule:work`, so invitation mails, the lapse listener and the ownership-transfer listener ran on the real worker. Mail goes over SMTP to Mailpit.
- Both `2026_10_07` migrations were already applied. The dev database was not reset, seeded or put into maintenance mode, and other agents could use the app during the run.
- People were seeded through `UserFactory` and `ProfileFactory` as `qs016-<role>-<run>@example.test` and signed in through `POST /auth/login`. Display names were set through `PUT /me/profile`.
- Plus was granted with `OperatorSubscriptions::grant` (an operator id generated as a UUID), and lapsed with `OperatorSubscriptions::revoke`. That path dispatches `SubscriptionLapsed`, and the queued `DemoteOnLapse` listener ran on the worker.
- Expiry: one invitation's `expires_at` was moved 1 minute into the past, then `dev sharing:expire-invitations` ran.
- Auto-confirm of a departed member's rule: after the member left, the rule's first occurrence was moved to today in the database, then `dev wallets:materialise-occurrences` ran.

**Result**
- 285 checks in 22 scripted groups (TC-000 to TC-021), plus 17 exploratory probes (TC-030). Every check passes in its final form.
- The probes covered:
  - concurrent acceptance of one link by three people (1×200 + 2×404);
  - concurrent identical creates (one 201 with `share_url`, three 200 without);
  - inviting your own address (201; accepting is a no-op);
  - a removed member re-using their used token (404), and the same member re-invited (a new membership record);
  - invitations on an archived wallet;
  - `invitation` as a batch item (422 envelope);
  - reusing an invitation id from another wallet, or another record's id (404);
  - the token-in-path form (no route);
  - `UNKNOWN_FIELD` on a token body.
- `sharing.yaml` and `sync.yaml` were not changed.

**Clean-up**: every QA and E2E person, wallet, invitation, membership, transaction, rule, occurrence, category reference, activity entry and subscription was deleted afterwards (`storage/app/private/qa016/cleanup.php`, not committed). The totals were 84 people, 28 wallets, 165 invitations and 347 activity entries. The 57 Mailpit messages to `qs016-*` addresses were deleted too. Audit entries stay, because the table is append-only by design. Rate-limiter counters expire on their own.

**Evidence**: `qa/responses/TC-*.txt`. Credentials, invitation tokens and share links are redacted.

## Failure Details

### Product defect (fixed)

- **Unregistered-address mail copy (TC-001)**: the English line read "create an :app account". With the dev app name this rendered as "create an saveme-backend account", and with "Save Me" it would read "an Save Me account". `app/Modules/Sharing/Http/Lang/en/mail.php` now says "To join, first create a :app account with this email address, then open the invitation." The Arabic string was already correct.

### Test-side corrections (no product defect)

- TC-008 (first run): the invitation create was 403 `sharing.max_members_per_wallet`. The wallet was already at 5 (owner, 2 members, 2 pending), so the refusal was correct. The script now revokes one pending invitation first, and frees the seat again after TC-009.
- TC-010: the script expected a past-expiry invitation to leave the list before the sweep. The frozen contract (`listInvitations`) says it stays listed as `pending` until the hourly sweep. The check now asserts that, and that it is gone after the sweep.
- TC-015/016: expense transactions need `category_id`. The script now uses a platform expense category.
- TC-002: a malformed path id is a top-level 422 `INVALID_ID`, not a field error.
