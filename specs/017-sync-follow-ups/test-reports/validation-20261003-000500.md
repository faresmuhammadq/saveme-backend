## Observational Notes

### Partners see a member's new name — Scenario 6

- ⚠ The first in-run latency check failed: median 431 ms for a timezone save against 482 ms for a rename, over HTTP. Those samples were taken while the worker was re-stamping the previous rename's 120 wallets and while `composer test` was running in the same container. A controlled probe ran next (`http/us2-s6-timing.txt`): alternating samples, with the queue idle before each call. It gave a median of 439 ms for a timezone save against 411 ms for a rename, and a p95 of 454 ms against 465 ms. The difference is within noise. The request itself only queues the listener. In-process numbers in plan N-15 are 105 ms against 108 ms at p95. The dev web stack is slow in absolute terms because the full suite was running alongside.

### A refresh reads only the wallets that changed — Scenario 3

- The first run's recurring-rule body was incomplete (422), so that sub-step was skipped. The second run used the full `RecurringRuleWrite` body (201). The rule and occurrence rows both moved the head.
