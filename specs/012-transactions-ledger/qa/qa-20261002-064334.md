# QA Report: Transactions Ledger (spec 012, B6)

**QA Mode**: CLI QA (HTTP via curl against the running dev app; database state through `dev tinker`)
**Date**: 2026-10-02
**Feature**: [spec.md](../spec.md)
**Environment**: Fedora Linux 44 (kernel 7.2.7) host, `dev` container with PHP 8.5 and PostgreSQL 16, http://saveme-backend.test/api/v1
**Verdict**: ✅ ALL PASSED. Two defects were found, fixed and retested (TC-017, TC-033).

---

## QA Summary

All five transaction operations were exercised against the live dev stack, together with the ledger obligations they settle on wallets, categories and profiles.

**Setup**
- The dev database was migrated and seeded (`dev migrate`, `dev db:seed`, `dev queue:restart`).
- Four people were created through `UserFactory` in `dev tinker`:
  - A, verified;
  - B, verified, an editor of A's Cash wallet and the owner of a household wallet in which A is an editor;
  - C, verified, a viewer of A's Cash wallet and the owner of a wallet in which A is a viewer;
  - U, unverified.
- Each person signed in through `POST /auth/login`.
- Memberships were inserted directly under the wallet scope sequence, as spec 010 QA did, because invitations arrive in B9.
- A and C were given profiles through `Profile::factory()` for the default-currency checks, because factory users have no profile.

**Coverage**
- every acceptance scenario of US1–US5;
- balances on one wallet and on both wallets of a transfer, after every create, edit, delete and restore;
- transfer role rules from either path;
- `CURRENCY_MISMATCH` at both pointers;
- the currency lock, which holds even when the wallet's only transaction is deleted;
- `IMMUTABLE_FIELD` for kind and destination;
- `VERSION_CONFLICT` with `current`;
- DELETE with a JSON body, giving an idempotent tombstone;
- restore via `PATCH {deleted_at:null, version}`, which rebalances both wallets;
- `CATEGORY_IN_USE` over HTTP, including a category used only by a tombstone;
- category references published to a shared wallet, visible to an editor and a viewer, and withdrawn when the category is moved away;
- the list grammar: sort, every filter and operator, search (case, `%` and `_` taken literally), and a three-page cursor walk;
- `EMAIL_NOT_VERIFIED` on every write;
- `meta` returned as `{}`;
- archived wallets and categories accepted;
- the wallet-deletion cascade;
- server-owned members refused as `UNKNOWN_FIELD`;
- five concurrent stale PATCHes sent through both wallet paths;
- four concurrent identical creates;
- `wallets:verify-balances` (0 drift).

**Result**: 173 checks: 171 passed on the first run, and 2 failed. Both were defects, fixed in this change and passing on retest.

1. **TC-033: repeated `filter[date]` silently dropped a condition.** `?filter[date]=gte:…&filter[date]=lte:…` is the form that api-conventions and the OpenAPI `Filter` parameter (deepObject, "Repeating a field ANDs its conditions") document. PHP's query parser kept only the last value, so the range collapsed to `lte` and returned a plausible page of wrong rows. Only `filter[date][]=` worked. **Fix**: `CollectionQuery` now reads `filter[...]` pairs from the raw query string, so a repeated field ANDs (the `[]` form still works). It is shared code, so wallets and categories benefit too.
2. **TC-017: inconsistent answer on a transfer's other wallet.** B owns the destination wallet but is not a member of the source. B's PATCH of the transfer through the destination path answered `422 INVALID_ENUM_VALUE` at `/counter_wallet_id`, a field B cannot change, while DELETE in the same situation answered `403`. **Fix**: through the destination's path, editing or restoring a transfer without being a member of its source is now `403 FORBIDDEN`, as DELETE already was. Row T-03 does not hold in the source, `counter_wallet_id` names the caller's own wallet, and the spec 012 precedence places that check at 403. Through the source path, a destination the caller is not (or no longer) a member of stays `422` at `/counter_wallet_id`, because FR-006 and FR-014 require it. Recorded as an assumed default in spec.md Edge Cases.

## Failure Details

### TC-033: repeated `filter[date]` ANDed (US4·2)

- **Steps**: `GET /wallets/{id}/transactions?filter%5Bdate%5D=gte:2026-09-10&filter%5Bdate%5D=lte:2026-09-13`
- **Expected**: 2026-09-13, 2026-09-12, 2026-09-10
- **Actual**: 2026-09-13, 2026-09-12, 2026-09-10, 2026-09-01, 2026-08-20. The `gte` bound was dropped.
- **Cause**: PHP's `$_GET` keeps the last value of a repeated key, and `CollectionQuery::filters()` read `$request->query('filter')`.
- **Fix**: `app/Http/Api/Collections/CollectionQuery.php` parses the `filter[...]` pairs from `QUERY_STRING`. Regression test: `tests/Contract/Wallets/Transactions/ListTransactionsTest.php`, "a repeated filter field ANDs its conditions".
- **Retest**: ✅ `responses/TC-033.txt` (after the marker).

### TC-017: non-member of a transfer's source edits it through the destination (FR-024)

- **Steps**: B owns WB and is not a member of WA2. A records a transfer WA2 → WB. B sends `PATCH /wallets/WB/transactions/{tid}` with `{memo, version}`.
- **Expected**: `403 FORBIDDEN`, because T-02 does not hold in the other wallet, as with DELETE.
- **Actual**: `422 INVALID_ENUM_VALUE` at `/counter_wallet_id`.
- **Fix**: `TransactionService::authorizeOther()` refuses a non-member of the source, when the path names the destination, with `WalletActionForbidden`. Regression test: `tests/Feature/Wallets/Transactions/TransactionAuthorizationTest.php`, "a member of only one wallet of a transfer may read it there but not edit, restore or delete it".
- **Retest**: ✅ `responses/TC-017.txt` (after the marker).
