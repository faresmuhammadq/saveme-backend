# QA Report: Reports (spec 019, B13)

**QA Mode**: CLI QA. HTTP driven by Python `requests` (curl-equivalent) against the dev app, http://saveme-backend.test/api/v1. Every figure was cross-checked against an independent Python model built from the raw transactions the script created (postings, categories, occurrences listed through the API). PHP in the `dev` container was used to grant Plus, to corrupt and restore one `balance_minor`, and to clean up.
**Date**: 2026-10-05 (server UTC 2026-10-04 21:00)
**Feature**: [spec.md](../spec.md)
**Environment**: Fedora Linux 44 host; `dev` container PHP 8.5, PostgreSQL 16; migration 2026_10_08_000001 applied.
**Verdict**: ALL PASSED. 2021 checks in 11 groups, 0 failures. No product defect found; `reports.yaml` v1.11 unchanged.

## Setup
People registered through `POST /auth/register`, verified from Mailpit, signed in (a, b, d, x verified; u left unverified). Plus granted to a and b. Wallets: CASH (shared with b), BANK, CARD (credit card, opening -30000), USDW (USD), ARCH (archived), DEL (deleted; has a live transfer into BANK), P and LEFTW (b owns; a joined, transacted, then left), BW (b only, 777777 platform groceries that must never reach a's reports), XW. 40+ transactions across April-November 2026, a deleted tombstone, an edited (re-dated and re-categorised) one, five recurring rules (rent, due salary confirmed, internal transfer, skipped, gam'eya with payout, USD rule). Responses are in `qa/responses/TC-*.txt` (credentials redacted).

## Coverage of the brief
- Wallet summary, by-category, trend: income, expenses, net, transfers_in/out, balance_start/end identity; transfers never income or expense; both members' transactions counted in a shared wallet (a and b identical for summary, by-category and trend).
- Range defaults: Budget Period containing `date` (also equal to `/budgets/{id}/progress` period for five dates), start day 25 change (transitional bucket 10-01..10-24), explicit from/to up to 366 days (inclusive; leap year too), 367 and 2 years give 400.
- months 1, 2, 12 accepted; 0, 13, -1, x, 1.5, 6abc, 100 give 400 (never clamped); empty value = absent.
- include_planned: scheduled occurrences only, in planned figures only (summary, per-item, trend series), confirmed and skipped excluded, payout counted as income, internal transfer rule absent from the cross-wallet planned transfers, actual figures and balances identical with and without the flag; unmaterialised months show less planned money (documented).
- Cross-wallet: default currency from the profile (a person with no transaction yet set USD), `currency=` override, `meta.excluded_wallets` sorted, archived wallets in, left wallet out, deleted wallet's live transfer counted as transfers_in, internal transfers nowhere, boundary transfer into a wallet the caller left counted as transfers_out; JPY with no wallet gives 200 zeros with every wallet excluded. Unknown/invalid currency (ZZZ, egp, XX, EGPP, 123, E1P, usd) gives 400 on all three.
- Access: 401 (none and garbage), 422 INVALID_ID before 404, 404 for non-member, left, deleted, other's, unknown wallet (before any 400), 406, 426, 405 with Allow, unverified user allowed, viewer role allowed, Idempotency-Key harmless.
- Labels are machine keys (system_key, category id, period start date); partner's category id present; `meta` is `{}` on wallet reports; no percentage/share member anywhere (recursive scan of every response); tombstones excluded; delete/restore/redate/recategorise/transfer delete reflected on the next read.
- Truth: a corrupted `wallets.balance_minor` changes nothing; `balance_end` of a full-history range equals `GET /wallets/{id}.balance_minor` for all five own wallets (and after concurrent writes).
- Concurrency (best effort): 60 writes by one member while four readers issued 100 summaries (wallet, cross, full-history, planned); the identity held in every response, no 5xx, the income figure moved between reads (so writes truly overlapped).
- Timing: cross-wallet summary 124-158 ms over 10 reads on the small QA ledger.

## Observations (not failures)
- Registration is throttled at 10/hour per origin; the QA hit it once during setup and only that counter was cleared.
- The profile timezone check can only prove the month, since Oct 4/5 share one Budget Period; the day-level timezone behaviour is covered by the Feature tests.
- Default currency cannot change after the first transaction (spec 008), so the default-currency case used a fresh person who set USD first.
- KWD (exponent 3) and a currency-mismatched occurrence were not reproducible through the API; they stay covered by the automated tests.
