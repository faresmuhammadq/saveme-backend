# QA Report: Sync Protocol (spec 013, B14)

**QA Mode**: CLI QA (HTTP via Python `requests`, curl-equivalent, against the running dev app; database state and signed test cursors through `dev tinker`; `dev sync:purge-tombstones`)
**Date**: 2026-10-02
**Feature**: [spec.md](../spec.md)
**Environment**: Fedora Linux 44 (kernel 7.2.7) host, `dev` container with PHP 8.5 (Xdebug `develop` mode loaded in the web runtime) and PostgreSQL 16, http://saveme-backend.test/api/v1
**Verdict**: ✅ ALL PASSED (functional). One defect found, fixed and retested (TC-032). One indicative timing check (TC-043) is over target on the Xdebug-loaded dev web stack; this is an environment limit, not a defect (see Failure Details).

## QA Summary

**Setup**
- `dev queue:restart`. The dev database already had the four `2026_10_04` migrations. It was not reset, and maintenance mode was not used.
- Each run seeded four fresh people through `UserFactory` in `dev tinker`, with emails `qa013-{a,b,c,u}-<run>@example.test`:
  - A, verified, with a profile;
  - B, verified, with a profile;
  - C, verified, with no profile;
  - U, unverified, with a profile.
- Each person signed in through `POST /auth/login`.
- Memberships were inserted under the wallet scope counter. The member's user counter was stamped through the factory, so wallet first, then user, as ADR-0017 orders it. Invitations arrive in B9.
- Cursors "ahead of the scope" were minted with the server's own signer in tinker. The client cannot forge one.
- Tombstones were aged by updating `deleted_at` in tinker, then `sync:purge-tombstones` was run.
- All QA and E2E people and data were removed afterwards.

**Coverage**
- User feed:
  - profile, sessions, own categories and own memberships;
  - every row identical to its read endpoint;
  - platform categories and other people's records never appear.
- Wallet feed:
  - wallet, members, category references, transactions and transfers in;
  - every row identical to its read endpoint;
  - no postings.
- Transfers appear identically on both wallets' feeds, including to a destination member who is not a member of the source.
- Paging: limits 2, 50 (default) and 500 (clamped to 200); invalid limits refused.
- `sync_cursor` is never null, and an empty page returns the same cursor.
- Incremental reads: a record edited twice arrives once; tombstones are included.
- `INVALID_CURSOR` for:
  - garbage;
  - a tampered cursor;
  - another account, another feed or another scope;
  - a cursor ahead of the scope (both feeds).
- `filter`/`sort` refused; a stray `since` is ignored.
- `404` for a non-member or unknown wallet; `422 INVALID_ID`; `401`.
- Deleted wallets:
  - a former member can read a deleted wallet that has not been purged;
  - the member's user feed carries the tombstoned membership;
  - after the purge, the wallet feed is `404` and the stale user cursor gets `410`.
- `410 SYNC_CURSOR_EXPIRED` on both feeds, scoped to the purged scope only.
- Purge:
  - 91-day tombstones are removed and 89-day ones are kept;
  - horizons are raised on W1, A and B (membership);
  - a second run removes 0;
  - a referenced tombstoned wallet is kept.
- Gap safety: three concurrent writers while a reader pages both feeds; none of 80 writes missed.
- Batch:
  - mixed types applied in order;
  - independent outcomes (applied, conflict with `problem.current`, rejected 422/404/409/403);
  - pointers rooted at the item's `data` (`/amount_minor`, identical to the single `PUT`);
  - limits 1–50 (0 and 51 give `OUT_OF_RANGE /items`, nothing applied; 50 accepted);
  - every envelope refusal pointer;
  - `MALFORMED_JSON` and `415`;
  - profile items (own id, foreign id, unknown id, caller with no profile);
  - replay idempotency, with an `Idempotency-Key` ignored;
  - `EMAIL_NOT_VERIFIED` per item for an unverified caller (the profile item is applied);
  - delete, delete again, restore, and restore with `{version}` only;
  - transfer delete and restore through the destination path;
  - the same record three times in one batch;
  - per-record `PUT` unchanged;
  - an identical problem body for the same stale write sent alone and as an item;
  - `Accept-Language: ar` gives `Content-Language: ar` and localised item problems;
  - `meta` is `{}`.
- Logs: the `sync_batch` and `sync_feed_read` lines carry no ids, names, amounts or credentials.

**Result**: 141 checks: 140 passed, and 1 was indicative timing (⚠️ environment). One defect was found during exploratory probing, fixed and retested.

1. **TC-032: profile item from a caller without a profile row answered `500 INTERNAL_ERROR`.**
   - **Cause**: `RouterItemDispatcher::assertOwnProfile` called `Profiles::find()`, which throws `ModelNotFoundException` when the caller has no profile. The dispatcher's catch-all rendered that exception as a 500.
   - **Effect**: the problem was reported to the error log and marked retryable, so the phone would retry forever.
   - **Fix**: a missing profile is now `404 NOT_FOUND`, the same answer as a foreign profile id.
   - **Regression test**: `tests/Contract/Sync/BatchParityTest.php` ("a profile item from a caller with no profile row is 404 NOT_FOUND, never a 500").
   - Real accounts get a profile at registration, so the exposure was limited.

**Spec wording corrected (no contract change)**
- spec.md Clarifications listed "not an object" among the 422 envelope refusals. A body that is valid JSON but not an object is `400 MALFORMED_JSON`, as api-conventions requires for every endpoint and as `sync.yaml` already lists. The spec now says so.
- An *item* that is not an object stays `422 INVALID_TYPE` at `/items/{n}`.

## Failure Details

### TC-032: profile item from a caller with no profile (fixed)
- **Steps**: C, a person with no profile row, sends `POST /sync/batch` with one `profile`/`upsert` item.
- **Expected**: the item is `rejected` with `404 NOT_FOUND`.
- **Actual before the fix**: the item was `rejected` with `500 INTERNAL_ERROR` (retryable), and the error was reported to the log.
- **After the fix**: `404 NOT_FOUND`.
- **Evidence**: `responses/TC-032.txt`.

### TC-043: 50-item batch timing on the dev web stack (environment, not a defect)
- **Measured over HTTP through nginx**:
  - a 50-item batch of creates took 12.2–12.8 s;
  - a 63-row feed page took 0.7–0.95 s.
- **Why this is the environment, not the feature**:
  - The dev web runtime loads Xdebug in `develop` mode.
  - A single `PUT` transaction create on the same stack has a median of 777 ms, so the batch costs about 245 ms per item, which is 3x cheaper than sending the same writes one by one.
  - SC-006 is defined "with debugging extensions off". plan.md T046 measured p95 7.6 s (batch) and 148–225 ms (200-row pages) under that condition.
- **Residual risk**: the batch target has little headroom (7.6 s against 8 s). Production must run without Xdebug.
