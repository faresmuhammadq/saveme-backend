# SpecKit Test Validation Report

**Feature**: specs/014-recurring-transactions
**Spec**: specs/014-recurring-transactions/spec.md
**Date**: 2026-10-02 14:30:05
**Overall Status**: ✅ PASSED (31 passed, 0 failed)

The feature is a JSON API with no UI. Every acceptance scenario was run end to end over HTTP instead of in Playwright. The script used Python `requests` (curl-equivalent) against http://saveme-backend.test/api/v1, with the headers `X-Client-Platform: android` and `X-Client-Version: 1.0.0`.

**Setup**
- QA people were seeded through `UserFactory` and signed in through `POST /auth/login`:
  - A, verified, owner, Africa/Cairo;
  - B, verified, editor, Asia/Dubai;
  - V, verified, viewer;
  - N, verified, non-member;
  - U, unverified editor.
- A fresh wallet "QA014 E2E" was created over the API. Memberships were inserted under the wallet scope counter.

**Server side**
- The job ran for real: `dev wallets:materialise-occurrences`.
- Purge ran for real: `dev sync:purge-tombstones`.
- Time travel was done only within the 90-day backfill, by moving a rule's internal `auto_confirm_from` in tinker. Wallet roles were changed in tinker to simulate the author being demoted.

**Evidence**: every request and response is under `test-reports/http/<scenario>.txt`.

## Observational Notes

### US1-6 month-end
- ⚠ April 30 and February monthly clamping cannot be seen over HTTP on 2026-10-02: the horizon is today + 35 days and the backfill is 90 days. Instead the run checked:
  - the 31st clamping to 30 September and returning to 31 October (no drift);
  - a 29 February yearly anchor giving 2027-02-28.
- April and February monthly clamping is covered by `tests/Unit/Wallets/Recurring/RuleDatesTest.php`.

### US2-4 races
- In the member-versus-job race, the member's confirm landed first (200). The job found nothing left to confirm. Exactly one transaction exists. The opposite ordering is covered by `AutoConfirmRaceTest`.

### US3-5 pause/resume
- A rule created as `paused` materialises no occurrences until it is resumed (FR-011: only rules that are not paused or ended are kept materialised).

### US4-1 gam'eya
- The payout occurrence is materialised together with its round, so it appears only once the payout round's date falls inside the horizon (today + 35 days). A gam'eya whose payout is months away shows it later.
- The C7 client previews dates locally (contract point 3), so it can show the payout date before then.

### Exploratory (not an acceptance scenario)
- A defect was found and fixed in the same session; see qa report TC-090.
- Changing `amount_minor` on a gam'eya rule or an `amount_basis: total` rule after a round was resolved re-split only the pending rounds. For example: 83,334 + 11 × 100,000 ≠ 1,200,000.
- `amount_minor` is now frozen (`IMMUTABLE_FIELD`) for those rules once any occurrence is resolved.
